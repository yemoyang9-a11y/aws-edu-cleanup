## 먼저 밝혀 둘 한계

- **같은 계정에서 원본 aws-nuke를 돌린 측정값은 없습니다.** 원본과의 비교는 소스 코드 동작과, 같은 로그에서 계산한 추정치로만 했습니다.

- 모든 실측은 **`b89f784` 이전 버전**으로 돌린 것입니다. 그 뒤에 바꾼 스택 처리(`b89f784`, `4c2ea10`)는 **실제 계정에서 아직 돌려 보지 않았습니다.**

### 읽는 법

- **스택이 없는 계정은 13~23분**이 걸렸습니다(A, E, B는 보고값 15~20분).
- **실습 스택이 있는 계정은 스택 대기가 전체 시간을 좌우했습니다.** F는 51분 중 31분(**62%**)이 스택 대기였습니다. 남은 스택은 VPC 안에서 돈 Lambda의 네트워크 카드(ENI)가 보안 그룹·서브넷을 붙잡고 있었던 것으로 보입니다. 미리보기에 해당 리전의 `EC2NetworkInterface`가 보인 것으로 판단한 [추정]이고, 스택 이벤트로 직접 확인하지는 않았습니다.
- **G에서 원본 aws-nuke의 스택 대기 문제가 그대로 나타났습니다.** 30분 스택 단계가 끝난 뒤에도 스택이 아직 삭제 실패·진행 중이었고, nuke가 그 스택을 다시 기다리며 53분 넘게 출력 없이 멈췄습니다. 로그 마지막 줄은 `CloudFormationStack ... retaining resource ...`였습니다. `4c2ea10`이 이 문제를 고친 수정입니다(실계정 미검증).
- E에서 nuke가 9분 걸린 이유는 **us-east-2 한 리전이 5분 00초**였기 때문입니다(다른 리전은 57초 이하). 4개 리전을 한 묶음으로 돌리기 때문에, 같은 묶음의 나머지 3개 리전도 그 5분을 함께 기다렸습니다.

## 4. 정확도와 오류

### 남은 리소스 (verify)

| | 값 | 근거 |
|---|---|---|
| 끝까지 결과를 확인한 삭제 실행 | 5개 (A, B, C, E, F) | [측정] A·B·C는 CLEAN 출력 확인, E·F는 1회차에 끝난 것으로 판단 |
| verify CLEAN | **5개 중 5개** | [측정] |
| 남은 리소스가 발견된 실행 | 0개 | [측정] |
| 잔여 발생률의 95% 신뢰 상한 | **45%** | [추정] 0/5에 대한 정확 이항 상한 (1 − 0.05^(1/5)) |

"5개 중 5개 CLEAN"은 **오류율이 0%라는 뜻이 아닙니다.** 표본 5개로는 잔여 발생률이 최대 45%여도 이런 결과가 나올 수 있습니다. 오류율을 의미 있게 말하려면 수십 개 이상의 계정 결과가 필요합니다.

verify가 확인하는 범위에도 한계가 있습니다.

- verify는 **79개 유형**(리전 74개 + global 5개)만 확인합니다. aws-nuke가 다루는 유형은 약 605개입니다. 목록에 없는 유형이 남아 있어도 CLEAN으로 나옵니다.
- 리셀러 SCP가 Cost Explorer를 막아서 **비용 기준으로는 교차 확인할 수 없습니다.** 최종 확인은 리셀러 청구서로 해야 합니다.

## 7. 데이터 추가하는 법

`b89f784` 이후 버전은 단계마다 시각을 기록하므로, 실행이 끝나면 정확한 단계별 시간 표가 결과 배너 바로 위에 나옵니다. 이미 끝난 실행은 같은 CloudShell에서 아래로 다시 볼 수 있습니다.

```bash
python3 ~/aws-edu-cleanup/tools/timing.py              # 가장 최근 실행
python3 ~/aws-edu-cleanup/tools/timing.py <계정번호>   # 특정 계정
```

이 표에 계정을 추가할 때는 계정 번호를 지우고, 근거 표시([측정]/[추정] 등)를 함께 적어 주세요.
